# Guidelines

## Rocq imports

Imports are grouped by origin, in this order, with a blank line between groups:

1. `Stdlib` (for example `Stdlib.micromega.ZifyNat`, then `Stdlib.ZArith.Zdivisibility`);
2. `stdpp`;
3. `iris`;
4. `zoo` and the other libraries of this repository: `zoo.prelude` first, then `zoo.common…`, `zoo.iris…`, `zoo.base`, the library modules (`zoo_std…`, …), the generated `__code`/`__types` files, and `zoo.options` last.

When adding an import, put it in its group rather than at the top of the file. Only add an import that is actually needed: check that the file does not compile without it, or that no other import already provides it.

Files generated by `ocaml2zoo` re-export the modules the OCaml code depends on. In particular, `<module>__types.v` has `Require Export` for every library module used by the implementation, for example `zoo_std.atomic_array`, `zoo_std.domain` and `zoo_std.sys`. When a proof file imports `<module>__types`, do not import these dependencies again: they are already in scope. Check the generated `__types.v` file before adding a `Require`.

## Rocq tactics

### Pure steps

Avoid redundant `wp۰pures` (tactics are defined in `theories/zoo/proofmode.v`):

- Use `wp۰apply+` instead of `wp۰pures. wp۰apply …`, and `awp۰apply+` instead of `wp۰pures. awp۰apply …`. The `+` variants take pure steps until the lemma applies. This includes recursive calls through an induction hypothesis: `wp۰apply+ ("IHfind_node_1" with "[…] HΦ")`.
- Tactics that execute one construct already start with `wp۰pures`: `wp۰load`, `wp۰store`, `wp۰xchg`, `wp۰cas`, `wp۰faa`, `wp۰tag`, `wp۰size`, `wp۰equal`, `wp۰match`, `wp۰block`, `wp۰block۰generative`, `wp۰ref` and `wp۰alloc`. Do not call `wp۰pures` before them.
- These rules hold even when other tactics come in between: in `wp۰pures. iDestruct … . destruct … . wp۰apply …`, the `wp۰pures` is redundant, because the tactics in between do not look at the program. Drop it and write `wp۰apply+`.
- `wp۰rec` only performs the β-reduction. Write `wp۰rec. wp۰apply+ …`, not `wp۰rec. wp۰pures. wp۰apply …`.
- Keep `wp۰pures` only when the next tactic needs the reduced program: a `rewrite` of a computed value (`rewrite (_ : (⁺˖lvl - 1)%Z = ⁺lvl)`), a `case_bool_decide` or a `rewrite bool_decide_eq_true_2` on a condition, a `destruct` whose branches start with different program steps, or the final `iApply "HΦ"`.

A program step (`wp۰pures`, `wp۰rec`, `wp۰apply`, …) is not followed by logical tactics on the same line: write `wp۰pures.` and then `iModIntro. iSplit; first done.` on the next line, not `wp۰pures. iModIntro. iSplit; first done.`. The exception is a branch that ends right away, such as `- wp۰pures. done.`.

### Applying specs

`wp۰apply` (like `wp۰apply+` and `awp۰apply`) binds the expression and introduces the postcondition, so it replaces the sequence `wp۰bind`, `iApply`, `iIntros` (see commit `ee37be9d`, which polished `theories/zoo_saturn/htbl.v`):

```coq
(* Do not write: *)
wp۰pures.
wp۰bind (domain٠recommended_domain_count _)%E.
iApply domain٠recommended_domain_countｰspec. iIntros "%sz %Hsz !>".

(* Write: *)
wp۰apply+ domain٠recommended_domain_countｰspec as "%sz %Hsz !>".
```

- Side goals stay after the `as` pattern: `wp۰apply (array٠unsafe_faaｰtype with "Hsizes") as "%n _"; first lia.`
- When the postcondition is `HΦ` (a tail call), pass it to the lemma: `wp۰apply (htbl٠resize₁ｰspec … with "[…] HΦ")`, not `iApply (…)`.
- To weaken the postcondition of a subexpression, use `wp۰apply` with `wpｰwand` too, and lay it out like this: a blank line before the `wp۰bind`, the predicate written one item per line (see Rocq statements), the intro pattern after `as`, the proof of the subexpression in a `{ … }` block, and a blank line after the block.

  ```coq
  wp۰pures.

  wp۰bind (𝗶𝗳 _ 𝘁𝗵𝗲𝗻 _ 𝗲𝗹𝘀𝗲 _)%E.
  wp۰apply (wpｰwand (λ v,
    ∃ n' x' : Z,
    ⌜v = (#n', #x')%V⌝ ∗
    ⌜random_height۰inv x0 n' x'⌝
  )%I with "[]") as "%v (%n1 & %x1 & -> & %Hinv1)".
  { wp۰pures.
    …
  }

  wp۰pures.
  ```

- Do not prove a `WP` as an assertion (`iAssert (∀ Ψ, … -∗ WP e {{ Ψ }})`) to use it once later. Do the steps where the expression is executed.

### Induction

Introduce the precondition first, then do the induction, generalizing the postcondition:

```coq
iIntros "%Φ (#Hequal & #Hkey & #Hentries) HΦ".

iInduction entries as [| entry entries] "IH" forall (Φ).
```

`iInduction` automatically reverts (and re-introduces in each case) the Iris hypotheses that mention the induction variable, so the induction hypothesis takes them as premises. This avoids `all: iIntros …` after the induction. When the induction hypothesis is a plain `WP` rather than a Hoare triple, `wp۰apply+ "IH"` still works.

### Pure facts from Iris hypotheses

- `iIntros "%x"` cannot introduce a universally quantified pure goal `⌜∀ x, …⌝`. To prove such a goal from Iris hypotheses, destruct what is needed first, then `iPureIntro`.
- When a lemma with a pure premise is used as `iDestruct (lemma with "H") as %…; first done.`, `done` may solve the premise by instantiating an evar with a trivial value (for example `v ≈ v`). Give the arguments that matter explicitly.
- Introducing a pure premise from a wand (`⌜φ⌝ -∗ P`) requires an affine BI; in generic lemmas, assume `BiAffine PROP`.

### Clear patterns

`iIntros` (and `iDestruct`) patterns can clear hypotheses (see `theories/zoo/iris/proofmode/intro_patterns.v`):

- `{H1 H2}` clears the Iris hypotheses `H1` and `H2`;
- `{#}` clears all intuitionistic hypotheses, `{∗}` all spatial hypotheses;
- `{$H}` frames `H` (in the goal);
- `{%}` clears all Rocq hypotheses that the goal does not depend on (like `clear`);
- `{% x H}` clears the Rocq hypotheses `x` and `H` (like `clear x H`);
- `{%- x H}` clears all Rocq hypotheses except `x` and `H` (like `clear - x H`).

Use them to merge `iModIntro`, `iIntros` and `iClear` into a single `iIntros`. For example, write `iIntros "!> H {H1 H2}".` instead of `iIntros "!> H". iClear "H1 H2".`, and `iIntros "!> {H1 H2}".` instead of `iModIntro. iClear "H1 H2".`.

### Assertions under an update

When an assertion is proved under a fancy update (for example by `iMod` of an atomic update), do not state it under the update (`iAssert (|={E}=> P)%I with "[…]" as ">H"`). Write the assertion itself and put `>` in the specialization pattern: `iAssert P%I with "[> H1 H2]" as "H"`. The `>` lets the proof of the assertion use the update modality of the current goal. This also works when the goal is a `WP` (for example to open an invariant with `iInv` inside the proof), and with no hypotheses for a pure fact: `iAssert ⌜0 < node.(node۰height)⌝%I with "[>]" as %Hheight`.

### Mutually recursive functions

To verify mutually recursive functions (`finish_as`/`finish`, `add_aux`/`add`, …), prove the conjunction of their specs in one lemma, by a single Löb induction (see `queue_mpmc_2٠push₁ｰspecｰaux` in `theories/zoo_saturn/queue_mpmc_2.v` and `mcas_1٠determine_asｰevalｰdetermineｰspec` in `theories/zoo_mcas/mcas_1.v`). Do not inline one function's spec into the other's proof, or prove one of them with an `iAssert`.

```coq
#[local] Lemma htbl٠finish_asｰfinishｰspec γ ι :
  ⊢ (
    ∀ s g buckets cap o,
    {{{ … }}}
      htbl٠finish_as γ s
    {{{ … }}}
  ) ∧ (
    {{{ … }}}
      htbl٠finish γ
    {{{ … }}}
  ).
Proof.
  iLöb as "HLöb".
  iDestruct "HLöb" as "(IHfinish_as & IHfinish)".
  iSplit.

  { iIntros "%s %g %buckets %cap %o !> %Φ (…) HΦ".
    …
    wp۰apply ("IHfinish" with "Hhtbl HΦ").
  }

  { iIntros "!> %Φ … HΦ".
    …
  }
Qed.
```

- The parameters that differ between recursive calls are universally quantified inside each conjunct. The parameters that stay the same (`γ`, `ι`, the key, …) are parameters of the lemma.
- Each conjunct is proved in a `{ }` block. Recursive calls use the induction hypotheses (`IH<function>`), passing the precondition explicitly. A step of the program (`wp۰rec`, `wp۰pures`, …) has to come first to remove the later.
- Then derive the individual specs from the conjunction, and use them everywhere else, even for a single call site: do not destruct the conjunction in another proof (`iDestruct (…ｰspec …) as "(_ & H)". wp۰apply ("H" …)`). For example:

  ```coq
  #[local] Lemma htbl٠finishｰspec γ ι :
    {{{ … }}}
      htbl٠finish γ
    {{{ … }}}.
  Proof.
    iDestruct htbl٠finish_asｰfinishｰspec as "(_ & H)".
    iApply "H".
  Qed.
  ```

### Modality introduction

`iModIntro` and the `!>` intro pattern also introduce the later modality `▷`, so `iNext` is just one more `!>`. Combine consecutive introductions: write `iIntros "!> !>".` instead of `iModIntro. iNext.`, and `iIntros "!> !> H".` instead of `iModIntro. iNext. iIntros "H".`.

## Rocq naming

Lemma names are made of components separated by `ｰ`, for example `array۰modelｰlookup`, `Zｰremｰmod` or `Zｰmodｰpow2ｰdouble`. A component is the name of the object the lemma is about (`array۰model`, `Z`, `is_pow2`), or a single property or operation (`lookup`, `mod`, `double`). Inside a component, words are separated by `_` (`of_nat`, `mul_r`). Do not use `_` to separate components, including for lemmas about `Z` or `nat`.

Variables have intuitive, full names: `entry`/`entries`, `cell`/`cells`, `waiter`/`waiters`, not `e`/`es`, `c`/`cs`, `w`/`ws`. Hypotheses follow the same names (`Hentries`, `Hcells_lookup`). Definitions use full words as well (`generations۰auth`, not `gens۰auth`); short names are fine for local variables that are used everywhere (`gens`, `gen`). Do not use capital letters for variables whose type lives in `Set`/`Type` (maps, sets, lists, …): name the ghost maps of an invariant after what they hold (`frozen`, `inited`), not `F` or `I`. Capital letters remain fine for propositions and predicates (`P`, `Q`, `R`), masks (`E`) and types (`K`, `A`).

## Rocq implicit arguments

Arguments that are determined by other arguments (typically the parameters of an invariant record, determined by the invariant hypothesis) should be implicit, so that uses do not need long runs of underscores. Write `inv۰pure۰model Hinv _ _ Hlookup`, not `inv۰pure۰model _ _ _ _ _ _ _ _ Hinv _ _ Hlookup`:

- for a lemma, put these binders in braces after its name: `Lemma inv۰pureｰlookup {𝘩𝑎𝑠𝘩 gens cur resizing m frozen inited waiters} : …`;
- for the fields of a `Record`, add `#[local] Arguments inv۰pure۰model {_ _ _ _ _ _ _ _}.` after it.

Use `Abbreviation` (not `Notation`, deprecated for this use) to name a term with parameters, such as `#[local] Abbreviation entries۰bucket entries := (entry۰binding <$> entries).`.

## Rocq data

Do not use tuples of three components or more (`val * val * Key`, which is really `(val * val) * Key`, accessed with `.1.1` and `.2`). Define a `Record` with named fields instead, for example:

```coq
Record entry Key := Entry
  { entry۰key : val
  ; entry۰value : val
  ; entry۰𝑘𝑒𝑦 : Key
  }.
```

Application binds tighter than any notation, so a record constructor needs no parentheses outside of an argument position: write `Entry key v 𝑘𝑒𝑦 ∈ entries` and `Entry key v 𝑘𝑒𝑦 :: entries`, not `(Entry key v 𝑘𝑒𝑦) ∈ entries`. Parentheses are still needed when it is an argument: `CellActive (Entry key v 𝑘𝑒𝑦 :: entries)`.

Pairs are fine. A variable may have the same name as its record type (`Implicit Type entry : entry Key.`), but then the type cannot be mentioned after the variable is bound in the same statement.

## Rocq ghost state

The ghost state of a module is declared once with `Zoo global`, which generates the class `<Module>G Σ …` that clients must provide. When the ghost state depends on a type chosen by the client (for example the type of abstract keys), make it a parameter of `Zoo global` instead of encoding it into a fixed type (`positive` through `encode`, `kmap encode`, …). `Zoo global` accepts type parameters and typeclass constraints on them:

```coq
Zoo global Key `{Countable Key} :=
  { model : twins (leibnizO (gmap Key val))
  ; frozen : ghost_map (nat * nat) (list (entry Key)) : iris
  }.
```

Then, in the section, write `Context `{htbl۰G : HtblG Σ Key}.` (without `!`): implicit generalization introduces `Key`, its instances and the `ZooG Σ` superclass. Do not also declare `Context {Key : Type} `{Countable Key}.`, which would duplicate the instances. See `theories/zoo_std/ivar_3.v` and `theories/zoo_saturn/channel_sync_1.v` for other examples.

## Zoo semantics

- Physical equality (`==`, CAS) on blocks: two non-generative blocks (tuples, records, ordinary constructors) compare equal when their fields are similar (`≈`), and all closures are similar. If the correctness of a CAS relies on block identity (for example a CAS on a bucket, a list node or a state record), mark the constructor `[@generative]` in the OCaml source; this has no effect on the OCaml runtime. Similarity of generative blocks gives equality of their fields.
- Constants defined in the OCaml code (`let min_buckets = 16`) are translated to values (`htbl٠min_buckets`). Do not repeat the literal (`16`) in the proof. Define the constant once from the generated value, prove its properties and its unfolding, and make both opaque (see `min_capacity` in `theories/zoo_saturn/ws_deque_1.v`):

  ```coq
  #[local] Definition min_buckets :=
    val۰to_nat' htbl٠min_buckets.
  #[local] Lemma min_bucketsｰis_pow2 :
    is_pow2 min_buckets.
  Proof.
    exists 4. done.
  Qed.
  #[local] Lemma htbl٠min_bucketsｰunfold :
    htbl٠min_buckets = #min_buckets.
  Proof.
    done.
  Qed.
  Opaque htbl٠min_buckets.
  Opaque min_buckets.
  ```

- Array values are abstract: do not assume they are locations. When a proof needs identity of arrays from similarity, use `array۰invｰsimilar` (`v ≈ t → array۰inv t sz ⊢ ⌜v = t⌝`) from `zoo_std.array`.
- A `match` on a value built by a Rocq function of an abstract argument (for example `bucket۰to_val l` with `l` unknown) does not reduce, so `wp۰pures` gets stuck. Do not duplicate or `iAssert` the continuation: declare a local `PureExec` instance that sends such a `match` to its fallback branch, with a computable side condition on the branches (see `pureｰmatchｰbucket` in `theories/zoo_saturn/htbl.v`). `wp۰pures` discharges the side condition with `simpl; done`, so give the definitions involved `Arguments … / : assert.`, otherwise `simpl` does not unfold them.
- Constructor tags follow OCaml: constant constructors and constructors with arguments are numbered separately, so different constructors can share a tag (`Init` and `Cons` both have tag 0 in `htbl`). A `match` branch is selected by its tag *and* its arity.
- Avoid lemmas about partial applications (for example a spec for the closure obtained by evaluating `array٠unsafe_get t`): library specs are stated for full applications, so a partial application in the code needs an extra lemma, often next to the library. If the verified code contains a partial application that would require such a lemma (for example `Atomic_array.initi n (Array.unsafe_get succs)`), detect it and suggest replacing it with an equivalent form that the existing specs cover, typically an eta-expansion (`(fun i -> Array.unsafe_get succs i)`), provided the change is small. Do not add the lemma instead.

## Rocq locality

Everything that is not part of the module API must not pollute clients. Mark it `#[local]`: definitions, fixpoints, lemmas, instances, `Arguments`, custom intro patterns, … This includes auxiliary arithmetic lemmas, internal representation functions (`…۰to_val`), ghost state wrappers, invariant components and the specs of internal functions. Only the public predicates (`…۰inv`, `…۰model`, validity predicates, …), their instances, and the public specs stay global. `Inductive` and `Record` cannot be made local; keep them as they are, but make their `Arguments` and instances local.

A `#[local]` instance declared inside a `Section` disappears at the end of the section. If it is needed after the section, add `#[local] Existing Instances …` right after `End`.

## Rocq abstraction

Do not break the abstraction of library data structures. For example, never unfold `array۰model` or `array۰inv` to reveal that an array is a location. Treat such values as abstract `val`s and only use the lemmas the library exports. If a missing property is needed, state it abstractly (for example, in terms of similarity `≈`) and prove it next to the library, not by exposing the representation in client proofs.

## Rocq statements

Statements are laid out one item per line:

- A quantifier goes on its own line, followed by its body at the same indentation:

  ```coq
  ∃ k,
  n = 2 ^ k.
  ```

- Premises (`→`, `-∗`, `={E}=∗`) end their lines and are aligned. When the conclusion is a compound formula (a quantifier, a conjunction, a disjunction, a separating conjunction), it is indented by two more spaces:

  ```coq
  is_pow2 n →
  1 ≤ m →
    ∃ a,
    1 ≤ a ≤ m ∧
    ((⁺a * step) `mod` ⁺n = j)%Z.
  ```

- A quantified premise or conjunct is put in parentheses, the opening parenthesis on the line of the quantifier and the closing one on its own line:

  ```coq
  ( ∀ k entries,
    cells1 !! k = Some (CellFrozen entries) →
    cells2 !! k = Some (CellFrozen entries)
  ) →
  ```

  The same goes for `assert`: `assert (` on its own line, the formula indented, `) as H.`. Under a modality, write `□ (` and put the body on the following lines. A quantified pure `iAssert` is laid out the same way, between `⌜` and `⌝`:

  ```coq
  iAssert ⌜
    ∀ j cell',
    cells' !! j = Some cell' →
    cell' ≠ CellInit
  ⌝%I as %Hinit.
  ```

- Conjunctions put one conjunct per line, `∧` ending each line but the last; as a compound conclusion, they are indented:

  ```coq
  1 < n →
    is_pow2 (n / 2) ∧
    n = 2 * (n / 2).
  ```

- Disjunctions put `∨` at the beginning of the continuation lines, the first disjunct being aligned with the others:

  ```coq
    cell' = CellInit
  ∨ ∃ entries,
    cells !! j = Some (CellFrozen entries) ∧
    cell' = CellActive entries.
  ```

  Inside a scope delimiter, the parentheses go on their own:

  ```coq
  ( h `mod` ⁺(2 * n) = h `mod` ⁺n
  ∨ h `mod` ⁺(2 * n) = h `mod` ⁺n + ⁺n
  )%Z.
  ```

- An Iris formula needs a single `%I`, around the whole term. Do not repeat it on subterms (`saved_pred η (λ b, True -∗ Φ #b)` inside an assertion already under `%I`). When a definition body is an `if`/`match` with Iris formulas in its branches, put the `%I` around the whole `if`, between parentheses, rather than in each branch. A disjunction in a branch follows the disjunction layout, indented from the `then`/`else`:

  ```coq
  #[local] Definition find_node۰token γ 𝑘𝑒𝑦 b Q : iProp Σ :=
    ( if b then
          Q None
        ∨ find_node۰commit γ 𝑘𝑒𝑦 b Q
      else
        find_node۰commit γ 𝑘𝑒𝑦 b Q
    )%I.
  ```

- The same layout applies to formulas written inside proofs: an `iAssert` of a separating conjunction or of a quantified fact, or a predicate passed to a lemma (`wpｰwand`, `array٠initiｰspec`, …), is laid out one item per line, the closing `)%I` on its own line:

  ```coq
  iAssert (
    nodes۰model nodes1 statuses1 ∗
    ⌜node.(node۰height) - status.(status۰marked) ≤ S lvl⌝
  )%I with "[Hnodes]" as "(Hnodes & %Habove)".
  ```

- Write `˖n` (from rocq-please) instead of `S n`; it often saves parentheses: `⁺˖n` instead of `⁺(S n)`, `inited۰elem γ ˖g j` instead of `inited۰elem γ (S g) j`.

- Do not put universal quantifiers in the conclusion of a lemma (or of a `Record` field): bind the variables with the lemma's parameters instead, after its name. Write `Lemma foo x y : P x → Q x y.`, not `Lemma foo x : P x → ∀ y, Q x y.`.

## Rocq spec order

Specs follow the order of the functions in the OCaml source, including submodules (for example `Bucket.assoc`, `Bucket.dissoc`, …, then `Buckets.cas_init`, `Buckets.take`, then `create`, `index`, …). Public and local specs are interleaved in this order; do not gather the public specs at the end of the file.

- Each function (or group of mutually recursive functions) gets its own header, `(* [create]. *)` or `(* [finish_as] and [finish]. *)`, after a separator line.
- Helper lemmas used only by one spec go just before it, under the same header.
- For mutually recursive functions, the conjunction lemma comes first. The specs derived from it, local or public, follow immediately (for example `htbl٠add_auxｰaddｰspec`, then `htbl٠addｰspec`).
- If a spec must move into the main section to follow this order, but it was in a separate section, make its section variables (such as `key۰model`) come from the main section's `Context`, and remove them from the call sites.

## Rocq proof style

Spacing matters for readability. Keep it consistent with existing proofs. Good reference files are `theories/zoo_saturn/bag_1.v`, `theories/zoo_saturn/stack_mpmc_1.v` and `theories/zoo_saturn/inf_ws_deque_1.v`.

1. **Spec proofs** (Hoare triples `{{{ }}}` and atomic triples `<<< >>>`): put a blank line after the first `iIntros`, the one that introduces the precondition and `HΦ`. This applies even when the next line is `iInv`.

   ```coq
   Proof.
     iIntros "%Φ (:inv) HΦ".

     wp۰rec. wp۰pures.
   ```

2. **Atomic sections**: an invariant opened with `iInv` (often just after `wp۰bind (…)%E.`) starts a block.
   - Put a blank line before the block, that is, before the `wp۰bind` if there is one.
   - The block runs until the invariant is closed: `iSplitR "…". { iFrameSteps. }` followed by `iModIntro.` or `iIntros "!> …"`.
   - Put a blank line after the block, before the next program step. For example, write `iModIntro.`, then a blank line, then `wp۰pures.`, not `iModIntro. wp۰pures.` on one line.
   - If the block ends the proof, nothing follows.

   ```coq
     wp۰pures.

     wp۰bind (𝗰𝗮𝘀 _ _ _)%E.
     iInv "Hinv" as "(:inv۰inner =1)".
     wp۰cas as _ | Hcas.

     - iSplitR "HΦ". { iFrameSteps. }
       iSteps.

     - iMod "HΦ" as "(%vs & (:model) & _ & HΦ)".
       …
   ```

3. **Case splits**: when a tactic in the main flow of a proof splits into branches (`wp۰cas as … | …`, or a `destruct` followed by bullets), put a blank line after it. Separate the `-`/`+` branches with blank lines.

4. **`iLöb`**: give it its own line, with a blank line before and after.

5. **Logical phases**: separate the phases of a proof with blank lines. Examples of phases:
   - `wp۰rec` and setup;
   - ghost allocations (`iMod …alloc`);
   - a `pose γ := {| … |}.` record;
   - registration through a fupd lemma;
   - the final `iApply "HΦ"`.

   Do not put blank lines inside a phase.

6. **No `all:` / `1:` / `2:` chains** to factor nearly identical branches. Prefer a uniform lemma, such as `wpｰcasｰnobranch'` instead of `wp۰cas`, or write explicit bullets.

7. **Bullets**: use `-` for the first level, `+` for the second level and `*` for the third level (then `--`, `++`, `**`). This applies at every place a new bullet context starts, including the top of a proof and inside a `{ … }` block, which starts again at `-`.

8. **`assert`**: use `assert (…) as H by tac.` only when `tac` is short (one or two tactics, such as `by lia` or `by (apply Nat.mod_small; lia)`). Otherwise, prove the assertion in a block:

   ```coq
   assert (j `div` cap = 1) as Hdiv.
   { symmetry. apply Nat.div_unique with (j - cap); lia. }
   ```

Helper lemmas that are not specs use a compact layout, with no blank line after `iIntros`. If a helper lemma opens an invariant, rule 2 still applies to that section.

## Rocq development workflow

Large verifications (`htbl`, `skiplist`, …) take minutes to compile, so do not iterate on the main file. Keep recompilation short by compiling only the proof being worked on:

1. **Work file.** Write the development in a work file outside the repository (in the scratchpad). It is the source of truth and always contains the real proofs.
2. **Fast file.** Generate from it a temporary file in the same theory, for example `theories/zoo_saturn/<module>_tmp.v`, and build only that file with `dune build theories/zoo_saturn/<module>_tmp.vo`. In the fast file, every `Proof. … Qed.` is replaced by `Proof. Admitted.`, except the lemmas listed in a WIP list (the ones being worked on). Generate it with a small script rather than by hand.
   - `Zoo global` names its class after the file (`SkiplistG` becomes `SkiplistTmpG` in `skiplist_tmp.v`): the script renames it.
   - For a lemma that is too big to recompile at each step (more than a minute), wrap its verified branches between `(* <admit> *)` and `(* </admit> *)` lines. The script replaces each region by `admit.` and ends the lemma with `Admitted.`. A region must be a whole bullet or `{ … }` body.
   - Once a lemma compiles, remove it from the WIP list: it is admitted from then on.
3. **Consistent signatures.** `please.options` sets `Default Proof Using "Type*"`, so admitted and proved lemmas may not take the same section variables. Typeclass hypotheses (for example `StrictOrder lt`) should be binders of the lemmas that need them, not section `Context`, so that the fast file and the final file agree.
4. **Bounded builds.** Wrap the build in `timeout` (a few minutes) and kill leftover `rocq` processes afterwards. A long build usually means an automation tactic failing slowly (`naive_solver` on an unprovable goal): replace it with explicit steps.
5. **Debugging.** Insert `Show.` before the failing tactic to print the goal in the build output.
6. **Final build.** At the end, write the main file from the work file with the markers removed, delete the temporary file, and build the main file in full, with no admits. Check `Print Assumptions` on the public specs.

When a library file must change (a lemma next to the library), develop the lemma first in a small temporary file of a dependent theory, then move it, because recompiling the library is slow.
